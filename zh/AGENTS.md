## 架构不变量

违反即打回，且每条都必须能被工具检查——**写不成 lint 规则的，不是不变量，是偏好**。

1. [依赖方向只允许 api → service → repo，禁止反向]
2. [所有外部请求走 `src/infra/http/`，业务层不直接发请求]
3. [数据库变更只走迁移脚本，禁止手改库]

## 禁止事项

- 不修改：[生成目录]、[构建产物]、锁文件、`.github/workflows/`、[vendor]
- 不引入新依赖，除非在交付说明里讲清现有依赖为何不够
- 不为让测试通过而改测试：不删断言、不加 ignore、不放宽 lint
- 不做需求之外的重构与全仓库格式化
- 不在代码、fixture、日志里写任何凭据或真实个人数据
- 架构层面变更（新分层、新目录、改依赖方向）先停下来问人

## 关键决策

代码里看不出来、但新人容易改错的地方。三到五条足够，写多了没人读。

- [为什么用 A 而不是 B，什么情况下这个决定会失效]
- [某个看起来多余的分层其实是因为 X，不要合并]
- [已知的历史包袱：某处写法不一致，不要照着改]

## 工作纪律

1. **先想再写**：动手前列出假设和不确定点；假设错了的代价远大于多问一句。
2. **简单优先**：只写需求要求的东西，不加"以后可能要用"的抽象、配置、开关。
3. **只改该改的**：不顺手重构、不重排 import、不格式化无关文件。
4. **目标驱动**：先确定"怎么算做完"，再循环到验证命令通过，而不是写完就算。

## 完成定义

- [ ] 验收标准逐条满足
- [ ] 测试、lint、类型检查实际跑过并通过（把输出贴进交付说明，不要只说"通过了"）
- [ ] diff 未超出需求涉及模块
- [ ] 若改了目录结构、分层依赖、公开接口或命令，**在同一个 diff 里更新本文件对应小节**

最后一条是这份文件不会过期的唯一原因：**文档更新是改动的一部分，不是后续任务。**
